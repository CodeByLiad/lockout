## The decision taken at the end of the session

The incremental restyle is **stopped**. The next branch rebuilds the UI from the ground up
against `docs/design/nuvetrix-app-design-system.md`, rather than continuing to adapt the
screens that exist.

The reason is worth recording, because it is the thing that went wrong here. This branch
replaced the *token layer* — palette, type, shape, motion — and then adapted the existing
widgets to consume it. That produced an app whose tokens are all house-correct and whose
screens still read as the old design wearing new colours. Three rounds of review kept finding
the same shape of defect:

- `MorphingSurface` and `ConnectedGroup` were built, tested and documented with no consumer.
- Shape-as-state constants existed for every surface; almost none reached a pixel.
- The hero card kept a neutral fill with an accent rail, against §8's accent fill, until the
  very end — and only a device screenshot caught it.
- The segmented control's house shapes turned out to be unreachable through a theme at all.

Each was fixed individually. The pattern was not: adapting a screen written for a different
design system tends to preserve that system's decisions in places no token can reach.

## What is worth keeping from this branch

The token layer is sound and tested, and the rebuild should keep it rather than redo it:

- `lib/theme/palette.dart` — house neutrals, both brightnesses, every role.
- `lib/theme/accents.dart` — the five accents, Rep lime `#C2EE7B` as identity.
- `lib/theme/lockout_motion.dart` — the three tiers.
- `lib/theme/cookie_border.dart` — lobed geometry, unit-tested as pure maths.
- `lib/theme/lockout_theme.dart` — the type scale and corner scale.
- `lib/theme/theme_controller.dart` — two axes, and a migration covering the six retired
  schemes *and* the eight pre-scheme keys before them. This one took real archaeology; do not
  rewrite it casually.
- `test/expressive_contract_test.dart` — the guard that asserts the app against the vendored
  house document. It has been strengthened four times, each time after it certified something
  false. Treat it as the main defence for the rebuild.
- The vendored house document itself, and its v1.1 amendments (Lockout's accent registered,
  the optional `numericTable` mono role).

## What the rebuild should treat as open

- **Screen composition.** Every screen's structure is in question, not just its tokens.
- **D7, five bottom-nav tabs.** §7.1 caps at four and this was deferred, not resolved. A
  ground-up rebuild is the right moment to settle it.
- **The house component catalog (§8)** — the six `NvButton` variants, filter chips, grouped
  lists, TBA card, wavy progress, snackbar, empty states. Branch 1 deliberately built none of
  these; a rebuild should start from them rather than from the screens.
- **§12's standard screens.** Welcome and Get Pro contradict the offline/no-auth/GPL stack and
  should stay unbuilt. About is feasible.
- **The copy sweep (§10).** Six tabs still carry all-caps copy. The contract guard's case rule
  is scoped to a file list for exactly this reason; widen it as screens land.
- **D9 and D10**, recorded this session: segmented-control segment shapes are not reachable
  through a Flutter theme, and the button press morph cannot honour reduced motion from a
  context-free `ThemeData`. A bespoke control would fix both.
